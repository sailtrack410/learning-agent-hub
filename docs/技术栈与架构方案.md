# 技术栈与架构方案

## 一、目的与范围

这份文档用于把前面已经确认的产品边界、数据模型、权限和状态机，进一步落成第一版可执行的技术栈与系统架构方案。

当前目标不是直接初始化代码仓，而是先明确：
- 第一版系统整体采用什么架构形态
- 后端、前端、存储、中间件分别怎么选
- 哪些能力先内聚在单体内，哪些不急着拆
- 开发时的工程结构和交付时的容器结构是什么关系

## 二、已确认前提

### 1. 产品与交付前提
- 单客户独立部署
- 单实例单企业
- 部署在客户自己的服务器
- 第一版交付目标为 Docker Compose

### 2. 架构前提
- 第一版采用模块化单体
- 不采用微服务
- 不引入平台级多租户

### 3. 存储前提
- 主业务库：MySQL
- 向量检索库：PostgreSQL + pgvector
- 缓存与会话：Redis

### 4. 前端前提
- 第一版先做 Web
- 管理后台与员工端拆成两个独立 Web 应用
- 员工端默认入口为消息

## 三、总体架构结论

### 1. 总体形态
- 代码层：单仓库
- 后端层：单 Spring Boot 业务应用，按模块划分包与服务边界
- 前端层：两个独立 Vue Web 应用
- 交付层：Docker Compose 编排多个基础服务与业务容器

### 2. 为什么不是微服务
- 当前业务边界还在收敛阶段，微服务会过早放大调用复杂度
- 审批、考勤、消息、Agent、知识库之间强关联较多
- 第一版更需要快速迭代和一致性，而不是分布式拆分

### 3. 为什么仍然适合容器化
- 容器化解决的是交付与运行环境一致性问题
- 模块化单体和 Docker Compose 不冲突
- 即使还是“普通项目写法”，也完全可以做成标准化部署包

## 四、总体拓扑

### 1. 逻辑拓扑

```text
employee-web  ─┐
               ├─> Nginx / Gateway ─> Spring Boot App
admin-web    ──┘                          ├─ 组织/权限/流程模块
                                          ├─ 考勤/假期模块
                                          ├─ 消息/群组模块
                                          ├─ 文档/知识库模块
                                          ├─ Agent/工具/连接器模块
                                          └─ WebSocket / 定时任务 / 异步任务

Spring Boot App ──> MySQL
Spring Boot App ──> PostgreSQL + pgvector
Spring Boot App ──> Redis
Spring Boot App ──> MinIO
Spring Boot App ──> SMTP
Spring Boot App ──> 模型服务 / 外部连接器
```

### 2. 运行拓扑建议

第一版推荐分两档：

- 开发档
  - `backend` 一个服务承担 HTTP、WebSocket、异步任务
- 生产推荐档
  - `backend-api` 负责 HTTP / WebSocket
  - `backend-worker` 负责 Agent 任务、知识入库、定时任务

### 3. 说明
- `backend-api` 与 `backend-worker` 可以使用同一份代码、同一镜像，通过不同启动参数区分职责。
- 这不属于微服务拆分，只是单体应用在运行层做角色分离。
- 这样可以避免 AI 与入库任务挤占 Web 请求线程。

## 五、后端技术栈

### 1. 主体框架
- JDK：Java 21
- 构建：Maven
- 主框架：Spring Boot 3.x
- 安全：Spring Security
- 会话：Spring Session + Redis
- ORM：MyBatis-Plus + MyBatis XML
- 审批流引擎：Flowable
- AI 编排：Spring AI
- 实时通信：Spring WebSocket
- 定时任务：Spring Scheduling
- API 文档：OpenAPI / Swagger

### 2. 选型理由
- Spring Boot 适合模块化单体快速起步
- Spring Security 与服务端会话模式配合成熟
- MyBatis-Plus 适合高频单表 CRUD
- MyBatis XML 适合复杂权限 SQL、报表和列表查询
- Flowable 负责流程定义、流程实例、任务路由，不自行从零造审批引擎
- Spring AI 用于统一模型、Prompt、工具调用、RAG 接入

### 3. 不建议第一版引入的后端组件
- 不引入微服务注册发现
- 不引入分布式配置中心
- 不引入消息队列作为必选依赖
- 不引入 Elasticsearch 作为第一版搜索底座
- 不引入纯 JWT 作为第一版主认证方案

## 六、后端模块划分建议

### 1. 代码组织原则
- 先做“逻辑模块化”，不急着做“物理服务化”
- 第一阶段建议保持一个 Spring Boot 应用
- 通过包结构、模块命名、服务边界控制耦合

### 2. 推荐模块划分
- `module-common`
  - 公共响应、异常、枚举、工具类、审计、基础配置
- `module-auth`
  - 业务用户登录、后台登录、会话、邮箱验证码、鉴权入口
- `module-org`
  - 组织、岗位、员工、直属上级、领导成员
- `module-admin`
  - 后台 RBAC、治理菜单、角色授权
- `module-workflow`
  - 申请单、模板、版本、审批动作、抄送、催办、委托
- `module-attendance`
  - 工作日历、班次、考勤组、排班、打卡、异常
- `module-leave`
  - 假期类型、规则、账户、余额流水
- `module-im`
  - 会话、群组、消息、WebSocket 推送
- `module-doc`
  - 文档空间、文档版本、文档 ACL
- `module-kb`
  - 知识空间、知识文档、入库任务、切片总账、检索服务
- `module-agent`
  - Agent 定义、版本、ACL、触发器、任务、工具调用、审计
- `module-connector`
  - 连接器定义、凭证元数据、外部系统调用封装
- `module-notify`
  - 邮件通知、系统提醒、待办投递、系统消息

### 3. 模块依赖原则
- `common` 可被所有模块依赖
- `auth` 依赖 `org` 与 `admin`
- `workflow` 可依赖 `org`、`leave`、`attendance`、`agent`
- `agent` 可以调用 `kb`、`connector`、`workflow` 提供的受控服务
- `im`、`doc`、`kb` 不直接互相强耦合，通过服务接口或共享底座交互

## 七、后端工程结构建议

### 1. 第一阶段建议

```text
server/
  pom.xml
  src/main/java/...
  src/main/resources/
```

### 2. 包结构建议

```text
com.workforcehub
  ├─ common
  ├─ auth
  ├─ admin
  ├─ org
  ├─ workflow
  ├─ attendance
  ├─ leave
  ├─ im
  ├─ doc
  ├─ kb
  ├─ agent
  ├─ connector
  └─ notify
```

### 3. 为什么先不做 Maven 多模块
- 你当前更熟悉普通项目开发
- 第一版更重业务闭环，不重构建拆分
- 等模块稳定后，再把包级模块演进为 Maven 多模块也来得及

## 八、前端技术栈

### 1. 共通技术
- Vue 3
- TypeScript
- Vite
- Pinia
- Vue Router
- OpenAPI 生成的共享 TS SDK

### 2. `admin-web` 建议
- UI 组件库：Element Plus
- 图表：ECharts
- 风格方向：标准 B 端治理型后台
- 适用原因：
  - 树、表格、表单、弹窗能力成熟
  - 与组织、流程、规则、治理页契合度高

### 3. `employee-web` 建议
- 基础能力：Vue 3 + TypeScript + Vite + Pinia + Vue Router
- UI 实现策略：自定义页面框架为主，通用基础组件可少量复用轻量组件库
- 动画策略：以 Vue Transition、CSS Transition、少量状态动画为主
- 风格方向：企业协同工具风格，消息优先，右侧详情栏默认收起

### 4. 为什么不建议员工端直接套后台模板
- 员工端默认入口是消息
- 交互密度、信息层级、布局模式都更接近协同工具
- 后台模板会把员工端做成“管理页缩小版”，不符合产品定位

## 十、数据与基础设施方案

### 1. MySQL
- 负责业务真相源
- 存储组织、账号、审批、考勤、消息元数据、Agent 配置、知识主记录等
- 第一版建议使用 InnoDB

### 2. PostgreSQL + pgvector
- 负责知识切片和向量检索
- 不作为业务真相源
- 用于 RAG 检索和相似度查询

### 3. Redis
- 负责登录会话
- 负责邮箱验证码
- 负责幂等键、限流键、短期缓存
- 后续如需要多实例广播，可扩展用于消息推送协调

### 4. MinIO
- 负责附件、文档文件、知识原文件对象存储
- 对应的元数据仍由 MySQL 中的 `sys_file_object` 维护
- 适合 Docker Compose 场景，私有部署成本低

### 5. SMTP
- 负责邮箱验证码与通知邮件发送
- 第一版支持绑定邮箱、找回密码、关键通知

## 十一、消息、推送与实时能力

### 1. 实时通信方案
- 后端：Spring WebSocket
- 协议建议：STOMP over WebSocket
- 前端：统一封装订阅客户端

### 2. 适用场景
- 新消息推送
- 会话已读回执
- 待办变化
- 审批状态更新
- Agent 任务状态更新
- 知识入库进度更新

### 3. 第一版边界
- 历史消息存 MySQL
- 实时推送走 WebSocket
- 不引入独立 IM 中间件

## 十二、异步任务与调度方案

### 1. 第一版方案
- 使用 Spring Scheduling + 应用内异步执行器
- 任务主记录直接落到业务表：
  - `agt_task`
  - `kb_ingest_job`

### 2. 为什么先不引入 MQ
- 当前是单体架构
- 异步任务规模可控
- 引入 MQ 会提高运维与一致性复杂度

### 3. 需要注意的点
- 所有异步任务必须可重试、可审计、可取消
- 任务线程池必须和 Web 请求线程池隔离
- 长耗时 Agent 与知识入库任务建议跑在 `backend-worker`

## 十三、认证与安全方案

### 1. 认证方案
- 业务用户：账号密码登录
- 管理员：后台独立账号密码登录
- 会话模式：服务端 Session
- 会话存储：Redis

### 2. 密码与账号安全
- 密码哈希建议使用 `BCrypt`
- 邮箱验证码只存 Redis，不落主表
- 登录、找回密码、敏感操作应有频控与失败次数限制

### 3. 凭证管理
- 外部系统凭证不存明文到业务数据库
- 数据库只存 `secret_ref`
- 实际密钥建议通过环境变量、挂载文件或独立密钥服务注入

### 4. 审计
- 管理员关键操作写 `sys_audit_log`
- Agent 工具调用写 `agt_tool_call_log`
- Agent 业务动作写 `agt_audit_log`

## 十四、Agent 与 RAG 技术方案

### 1. Agent 运行原则
- Agent 不是单一 Prompt
- Agent = 模型配置 + Prompt + 工具 + 知识绑定 + 触发器 + 权限 + 审计

### 2. AI 接入方式
- 统一通过 Spring AI 封装模型调用
- 模型接入通过配置或连接器做 provider 适配
- 第一版不并行引入多套 Agent 框架

### 3. RAG 方案
- 知识主记录在 MySQL
- 切片与向量在 PostgreSQL + pgvector
- 查询流程：
  - 用户问题进入 Agent
  - Agent 根据授权空间发起检索
  - 从 pgvector 返回相关切片
  - 结合主业务上下文生成回答

### 4. 工具调用方案
- 先定义 `agt_tool`
- 再通过 `agt_agent_tool` 做版本级授权
- 工具分只读、低风险写入、高风险写入
- 高风险写入默认不自动执行

## 十五、搜索与查询方案

### 1. 第一版建议
- 组织、审批、考勤、文档列表类查询以 MySQL 为主
- 知识语义检索以 pgvector 为主
- 不引入 Elasticsearch

### 2. 说明
- 这不代表永远不用搜索引擎
- 而是第一版先把结构化查询和 RAG 做稳，再决定是否加全文检索服务
