# 核心表结构草图

## 一、目的与范围

这份文档用于把《平台总导图》和《项目确认记录》落成第一版核心数据结构草图。

当前目标不是直接生成 SQL，而是先确定：
- 核心表有哪些
- 各表职责是什么
- 关键字段应该放哪里
- 表与表之间如何关联
- 哪些数据放 MySQL，哪些数据放 PostgreSQL，哪些数据放 Redis

## 二、设计前提

### 1. 部署与租户前提
- 系统采用单客户独立部署
- 单实例单企业
- 第一版不引入平台级 `tenant_id`
- 分公司、子公司按组织体系建模，不抽象为租户

### 2. 身份前提
- 员工、领导共用一套业务用户体系
- 管理员为独立后台账号体系
- Agent 为系统身份，不属于人类账号

### 3. 技术前提
- 主业务库：MySQL
- 向量检索库：PostgreSQL + pgvector
- 缓存与会话：Redis
- 审批流引擎：Flowable

### 4. 结构前提
- 第一版优先“强业务可读性”，不追求过度抽象
- 审批类业务采用“公共流程头 + 业务明细表”模式
- 知识库向量数据不是业务真相源，MySQL 中的知识文档主记录才是业务真相源

## 三、存储边界

## 1. MySQL 承担的内容
- 组织、人员、账号、权限
- 考勤、排班、假期、工龄
- 审批模板、业务申请、审批动作
- 会话、群组、消息元数据
- Agent 配置、任务、审计
- 知识文档主记录、入库任务、权限
- 连接器、凭证元数据、附件元数据

## 2. PostgreSQL 承担的内容
- 知识切片
- embedding 向量
- 相似度检索索引
- RAG 检索用元数据副本

## 3. Redis 承担的内容
- 登录会话
- 邮箱验证码
- 幂等键
- 限流键
- 高频缓存
- 短期任务状态

## 4. 不在本文展开的内容
- Flowable 引擎内置表
- Redis key 设计
- 搜索引擎索引设计
- 监控指标存储设计

## 四、通用建模约定

### 1. 命名约定
- 表名前缀按业务域划分：
  - `org_` 组织与人员
  - `auth_` 业务账号认证
  - `admin_` 后台账号与 RBAC
  - `att_` 考勤与排班
  - `lv_` 假期与余额
  - `wf_` 流程与审批
  - `im_` 会话与群组
  - `doc_` 文档
  - `kb_` 知识库
  - `agt_` Agent
  - `sys_` 平台共享能力

### 2. 主键约定
- MySQL 主键统一使用 `BIGINT`
- PostgreSQL 向量表主键可使用 `BIGINT`
- 业务唯一编码单独使用 `code` 或 `*_no` 字段，不用字符串做主键

### 3. 通用字段约定
多数 MySQL 业务表建议统一具备以下字段：
- `id`
- `created_at`
- `updated_at`
- `created_by`
- `updated_by`
- `is_deleted`

运行态/日志类表可按需要去掉 `is_deleted`，改为只追加不删除。

### 4. 状态字段约定
- 所有运行态对象显式保留 `status`
- 不用“是否完成”“是否有效”等多个布尔字段替代状态机

### 5. 快照约定
以下场景要保留快照，而不是只靠实时关联：
- 审批发起时的申请人部门、岗位、直属上级
- 审批节点的候选人和实际处理人
- 员工异动前后组织关系
- 假期扣减与发放时的规则口径

## 五、组织、人员与认证

### 1. `org_department`
- 用途：组织树主表，承载总公司、分公司、部门、班组等组织节点
- 关键字段：
  - `id`
  - `parent_id`
  - `tree_path`
  - `dept_code`
  - `dept_name`
  - `dept_type`
  - `dept_level`
  - `leader_user_id`
  - `status`
- 说明：
  - `leader_user_id` 表示组织意义上的第一负责人
  - 分公司、子公司通过 `dept_type` 区分，不单独建租户表
  - `tree_path` 用于快速做子树查询、数据范围判定、组织群同步等场景

### 2. `org_position`
- 用途：岗位/职务定义
- 关键字段：
  - `id`
  - `position_code`
  - `position_name`
  - `position_category`
  - `status`

### 3. `org_user`
- 用途：员工/领导业务主表
- 关键字段：
  - `id`
  - `employee_no`
  - `real_name`
  - `gender`
  - `mobile`
  - `primary_dept_id`
  - `position_id`
  - `manager_user_id`
  - `employment_status`
  - `hire_date`
  - `regularized_at`
  - `service_start_date`
  - `annual_leave_start_date`
  - `work_location`
  - `status`
- 说明：
  - `manager_user_id` 表示当前直属上级
  - 领导身份不在此表单独建角色字段，而由组织关系和领导表共同决定
  - `employment_status` 建议覆盖：待入职、试用期、在职、待离职、已离职

### 4. `org_department_leader`
- 用途：部门领导成员表，支持一个部门多个领导成员
- 关键字段：
  - `id`
  - `dept_id`
  - `user_id`
  - `leader_type`
  - `is_primary`
  - `sort_order`
  - `status`
- 说明：
  - `leader_type` 可取：正职、副职、代理负责人等
  - 用于审批候选解析、团队管理范围参考

### 5. `auth_user_account`
- 用途：业务用户登录账号表
- 关键字段：
  - `id`
  - `user_id`
  - `login_name`
  - `password_hash`
  - `password_salt`
  - `email`
  - `email_verified_at`
  - `account_status`
  - `last_login_at`
  - `password_updated_at`
- 说明：
  - 员工与领导共用这套账号
  - 邮箱验证码存 Redis，不单独设计数据库主表

### 6. `admin_user`
- 用途：后台管理员账号表
- 关键字段：
  - `id`
  - `username`
  - `password_hash`
  - `password_salt`
  - `display_name`
  - `email`
  - `status`
  - `last_login_at`
- 说明：
  - 管理员独立于业务用户体系
  - 即使现实中是同一个人，也不与 `org_user` 共用账号记录

### 7. `admin_role`
- 用途：后台角色定义
- 关键字段：
  - `id`
  - `role_code`
  - `role_name`
  - `status`

### 8. `admin_permission`
- 用途：后台权限点定义
- 关键字段：
  - `id`
  - `perm_code`
  - `perm_name`
  - `module_code`
  - `action_code`
  - `status`

### 9. `admin_user_role`
- 用途：管理员与角色关系
- 关键字段：
  - `id`
  - `admin_user_id`
  - `role_id`

### 10. `admin_role_permission`
- 用途：后台角色与权限关系
- 关键字段：
  - `id`
  - `role_id`
  - `permission_id`

## 六、平台共享底座

### 1. `sys_file_object`
- 用途：统一文件对象元数据，供消息附件、文档、知识库、审批附件复用
- 关键字段：
  - `id`
  - `storage_provider`
  - `bucket_name`
  - `object_key`
  - `file_ext`
  - `mime_type`
  - `file_size`
  - `content_md5`
  - `content_sha256`
  - `ref_count`
  - `upload_status`
  - `scan_status`
- 说明：
  - 文件名不参与物理去重，物理去重以 `content_sha256 + file_size` 为准
  - `storage_provider` 第一版支持 `LOCAL`、`MINIO`
  - `ref_count` 表示仍有多少业务引用指向该物理对象
  - `scan_status` 预留给防病毒与内容安全扫描，未通过扫描的文件不允许进入知识库或被 Agent 读取

### 2. `sys_attachment_ref`
- 用途：附件与业务对象关联表
- 关键字段：
  - `id`
  - `owner_type`
  - `owner_id`
  - `file_object_id`
  - `original_file_name`
  - `display_name`
  - `uploader_type`
  - `uploader_id`
  - `visibility_scope`
  - `sort_order`
  - `deleted_at`
  - `deleted_by`
  - `purge_after`
- 说明：
  - 同一物理文件在不同业务场景可有不同展示文件名
  - 用户删除文件时优先删除业务引用并进入回收站，不立即删除物理对象
  - `purge_after` 用于回收站到期后的彻底清理

### 3. `sys_upload_ticket`
- 用途：两段式上传票据主表
- 关键字段：
  - `id`
  - `ticket_no`
  - `uploader_type`
  - `uploader_id`
  - `biz_type`
  - `biz_id`
  - `storage_provider`
  - `bucket_name`
  - `file_name`
  - `mime_type`
  - `file_size`
  - `content_sha256`
  - `object_key`
  - `expire_at`
  - `status`
  - `confirmed_at`
- 说明：
  - 用于“申请上传票据 -> 客户端直传 LOCAL/MINIO -> 上传完成确认”链路
  - 上传完成后由确认接口创建 `sys_file_object` 并关闭票据
  - 票据过期后未确认对象进入临时清理流程

### 4. `sys_storage_quota_policy`
- 用途：云空间配额策略
- 关键字段：
  - `id`
  - `policy_code`
  - `policy_name`
  - `scope_type`
  - `scope_id`
  - `quota_bytes`
  - `cache_quota_bytes`
  - `warning_threshold`
  - `block_threshold`
  - `status`
- 说明：
  - `scope_type` 可取 `GLOBAL`、`USER_DEFAULT`、`DEPARTMENT`、`ROLE`、`GROUP`、`KNOWLEDGE_SPACE`
  - 支持系统默认个人空间、群空间、知识空间、组织长期文件池、临时缓存池

### 5. `sys_storage_usage`
- 用途：云空间占用统计
- 关键字段：
  - `id`
  - `scope_type`
  - `scope_id`
  - `used_bytes`
  - `cache_used_bytes`
  - `file_count`
  - `updated_at`
- 说明：
  - 配额是逻辑上限，不代表提前占用物理磁盘
  - 上传前需同时校验个人/空间配额、组织总池配额、存储后端真实可用容量

### 6. `sys_download_ticket`
- 用途：短期下载票据
- 关键字段：
  - `id`
  - `ticket_no`
  - `attachment_ref_id`
  - `requester_type`
  - `requester_id`
  - `download_type`
  - `expire_at`
  - `status`
  - `created_at`
- 说明：
  - 下载前先校验 `sys_attachment_ref` 权限，再生成短期票据或预签名 URL
  - 单文件下载链接建议 5-10 分钟有效，批量下载 ZIP 默认保留 7 天

### 7. `sys_todo_item`
- 用途：统一待办中心
- 关键字段：
  - `id`
  - `owner_type`
  - `owner_id`
  - `source_type`
  - `source_id`
  - `title`
  - `summary`
  - `route_path`
  - `status`
  - `priority`
  - `due_at`
- 说明：
  - 可承载审批待办、抄送、Agent 处理结果、文档待处理等
  - `owner_type + owner_id` 表示待办归属主体，第一版建议以 `org_user` 为主，必要时扩展到 `admin_user`、`agt_agent`

### 8. `sys_audit_log`
- 用途：统一审计日志
- 关键字段：
  - `id`
  - `operator_type`
  - `operator_id`
  - `action_type`
  - `target_type`
  - `target_id`
  - `result`
  - `detail_json`
  - `occurred_at`
- 说明：
  - 供管理员操作、Agent 动作、关键审批动作共用

### 9. `sys_connector`
- 用途：外部连接器定义
- 关键字段：
  - `id`
  - `connector_code`
  - `connector_name`
  - `connector_type`
  - `base_url`
  - `auth_type`
  - `status`

### 10. `sys_connector_secret`
- 用途：连接器凭证元数据
- 关键字段：
  - `id`
  - `connector_id`
  - `secret_name`
  - `secret_ref`
  - `status`
  - `last_rotated_at`
- 说明：
  - 不在数据库中保存明文凭证
  - `secret_ref` 指向密钥管理系统或加密存储位置

### 9. `kb_chunk_manifest`
- 用途：知识切片元数据总账
- 所在库：MySQL
- 关键字段：
  - `id`
  - `kb_document_id`
  - `ingest_job_id`
  - `chunk_no`
  - `chunk_hash`
  - `vector_row_id`
  - `status`
- 说明：
  - 用于把 MySQL 中的文档主记录和 PostgreSQL 中的向量行建立映射
  - 入库写入顺序建议为：先写 PostgreSQL `kb_vector_chunk`，成功后再写 MySQL `kb_chunk_manifest`
  - 如果 PostgreSQL 已写成功但 MySQL 总账写入失败，应把该批向量标记为待清理孤儿数据，不能直接把 `kb_document.ingest_status` 置为 `READY`

### 10. `kb_vector_chunk`
- 所在库：PostgreSQL
- 用途：向量检索主表
- 关键字段：
  - `id`
  - `kb_document_id`
  - `space_id`
  - `ingest_job_id`
  - `chunk_no`
  - `chunk_text`
  - `embedding`
  - `metadata_json`
  - `content_hash`
  - `is_active`
- 说明：
  - `embedding` 使用 pgvector
  - 该表用于检索，不作为业务真相源
  - 检索查询必须只命中 `is_active=true` 的切片
  - 当知识文档重建失败或被下线时，需要切换或关闭旧切片的可检索状态
  - 同一知识文档允许保留多次入库历史，因此切片唯一性应按 `ingest_job_id + chunk_no` 控制，而不是只按 `kb_document_id + chunk_no`

## 八、会话、群组与消息

### 1. `im_conversation`
- 用途：统一会话主表
- 关键字段：
  - `id`
  - `conversation_type`
  - `conversation_key`
  - `title`
  - `avatar_file_id`
  - `bound_agent_id`
  - `last_message_seq`
  - `last_message_id`
  - `last_message_at`
  - `status`
- 说明：
  - `conversation_type` 支持：私聊、群聊、Agent 会话
  - Agent 直聊会话通过 `bound_agent_id` 绑定
  - `conversation_key` 只用于约束私聊/Agent 直聊唯一性，群聊可为空
  - 私聊 `conversation_key` 建议按成员 ID 排序生成，例如 `private:user:12:user:34`
  - Agent 直聊 `conversation_key` 建议按用户与 Agent 生成，例如 `agent:user:12:agent:7`
  - 即使是 Agent 直聊，也仍建议在 `im_conversation_member` 中写入用户和 Agent 两类成员
  - `seq_no` 不应通过 `MAX(seq_no)+1` 生成，建议通过 Redis 原子递增或基于 `last_message_seq` 的行级更新分配

### 2. `im_conversation_member`
- 用途：会话成员表
- 关键字段：
  - `id`
  - `conversation_id`
  - `member_type`

  - `pin_flag`

  - `joined_at`
  - `left_at`
  - `status`
- 说明：
  - 群主/群管理员/成员均通过 `member_role` 表示
  - 私聊也使用该表表示两方成员

### 3. `im_group_profile`
- 用途：群组扩展信息，仅群聊类型会话使用
- 关键字段：
  - `id`
  - `conversation_id`
  - `group_type`
  - `binding_object_type`
  - `binding_object_id`
  - `owner_user_id`
  - `history_visible_mode`
  - `speak_mode`
  - `auto_sync_mode`
  - `notice_text`
  - `status`
- 说明：
  - `group_type` 支持：组织群、业务群、自定义群
  - 组织群可绑定 `org_department`，业务群可绑定流程、任务、项目等业务对象

### 4. `im_message`

## 九、流程与审批

### 0. Flowable 说明
- Flowable 引擎运行时表、历史表、定义表由引擎自行维护
- 当前草图只设计业务侧需要直连的表
- 业务表通过 Flowable 的 `process_instance_id`、`task_id` 等字段关联引擎数据

### 1. `wf_process_type`
- 用途：流程类型定义
- 关键字段：
  - `id`
  - `process_code`
  - `process_name`
  - `biz_type`
  - `status`

### 2. `wf_template`
- 用途：流程模板主表
- 关键字段：
  - `id`
  - `process_type_id`
  - `template_code`
  - `template_name`
  - `status`

### 3. `wf_template_version`
- 用途：流程模板版本表
- 关键字段：
  - `id`
  - `template_id`
  - `version_no`
  - `flowable_definition_key`
  - `flowable_definition_id`
  - `form_schema_json`
  - `rule_snapshot_json`
  - `published_by`
  - `published_at`
  - `effective_from`
  - `effective_to`
  - `status`
- 说明：
  - 一个模板多版本
  - 运行中的流程实例绑定发起时版本

### 4. `wf_request`
- 用途：统一业务申请头表
- 关键字段：
  - `id`
  - `request_no`
  - `biz_type`
  - `biz_id`
  - `applicant_user_id`
  - `applicant_dept_id`
  - `applicant_position_id`
  - `title`
  - `template_version_id`
  - `flowable_process_instance_id`
  - `agent_pre_review_task_id`
  - `status`
  - `current_step_key`
  - `current_step_name`
  - `submitted_at`
  - `finished_at`
- 说明：
  - 申请头负责统一列表、待办、历史查询
  - 业务明细由 `biz_type + biz_id` 指向具体申请表
  - 各业务明细表中的 `request_id` 是指向 `wf_request` 的强关联外键，`biz_id` 则是头表用于统一路由的反向索引，两者必须指向同一条业务明细
  - 申请人组织快照直接保存在头表
  - `agent_pre_review_task_id` 保存提交后触发的 Agent 预审任务 ID，后续回调必须匹配该 ID，避免错误 Agent 任务串写审批结果

### 1. `agt_agent`

- 关键字段：
  - `id`

  - `agent_name`
  - `agent_type`

  - `status`
